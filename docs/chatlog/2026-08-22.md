### 段落 3：嚴重事故——JSON.stringify 整檔重寫＋git checkout 誤用

Agent 為了把 `category` 值 `Reusable` 改小寫，寫了一個「讀取整個 JSON→修改物件→`JSON.stringify` 整檔寫回」的腳本，導致 `item-cards.json` 整檔排版被打亂（389 行新增/104 行刪除，不是預期的 8 個字小改動）。Agent 想「復原」這個誤改，執行了 `git checkout -- data/cards/item-cards.json`。

這個操作是錯的：這份檔案本來就是開發者還沒 commit 的進行中編輯（48 張卡、新的五分類系統），`git checkout --` 只會退回「最後一次 commit」（2026-08-18，26 張卡、舊分類），不是「agent 改壞之前」——結果把開發者尚未提交的道具卡編輯整個清空，git 完全沒有留下可復原的版本。Agent 立即停止操作，誠實回報事故經過、影響範圍、以及自己手上還留著的部分殘存資料（幾張卡的完整內容、category 統計）。

開發者：「這是一個非常嚴重的錯誤，我已經恢復文件內容，請提出後續工作流程避免再次發生相同錯誤的方法」

Agent 確認開發者已自行復原（唯讀方式核對，48 張卡、`category` 已是小寫），分析根本原因（三點：整檔重寫的做法本身、對 `git checkout --` 語意的誤判、執行前沒有先暫停檢查未提交變更），提出四條防範規則（JSON 資料檔案一律精準文字取代／視為無法靠 git 復原的高風險檔案，批次操作前先備份／絕不用 git checkout/reset/clean 復原自己的錯誤／不主動整檔重寫這幾份資料檔案），並存進 agent 記憶（`feedback_json_data_file_edits.md`）供之後工作階段自動套用。
