### 段落 7：room_action 測試情境與既有規則的衝突
Task 5 執行到「確認新測試會失敗」步驟時，其中一個測試（`game:selectAction room_action: resolves the current room's effects`，直接照抄計畫文件裡的程式碼樣本）失敗訊息是 `NOT_YOUR_TURN`，不是預期中的「功能還沒接上」錯誤。Agent 停下分析：這個測試的流程是「用 `game:move` 開門進新房間→立刻用 `game:selectAction actionType:'room_action'`」，但既有規則是「開新房間會把行動力直接歸零」，`game:move` handler 在這之後會呼叫 `advanceTurnIfOver`，AP 歸零代表回合立刻結束、換下一位玩家——同一回合內開門後不可能再有行動力觸發操作。這是計畫文件自己的測試案例情境跟既有規則互相矛盾，不是「還沒實作」的問題，於是停下向開發者確認方向，並提出兩個修正選項（直接操作 `gameState` 讓玩家已站在房間裡 vs. 模擬完整兩回合流程），推薦前者。

開發者先追加規則細節：

開發者：目前規則進入保險庫的當回合，確定不會有行動力可以立刻執行該操作，必須等到該玩家下一次輪到行動時，才能在該房間進行操作／考驗。依照當前規則，進入新房間不用跳出行動選單，因為行動力會歸零，所以不用考慮進入後的玩家行動。行動選單是回合開始時跳出，才有行動力可以移動、開門、道具、操作、襲擊等。

這段補充確認了「進房間自動觸發的卡片效果（抽卡）必須解析完才能結束回合」這個既有慣例是對的，但沒有直接回答 Agent 問的「操作是不是消耗獨立行動力的玩家主動選擇」。Agent 追問釐清兩種機制的差異（自動觸發的抽卡效果 vs. 玩家主動選擇消耗行動力的操作），開發者確認：

開發者：目前規則進入保險庫的當回合，確定不會有行動力可以立刻執行該操作，必須等到該玩家下一次輪到行動時，才能在該房間進行操作／考驗。

確認後採用推薦方案（方向 1）：測試改成用 `game:move` 真的開門（沿用既有board放置邏輯），開門後直接改寫 `gameState.currentPlayerIndex`/該玩家 `actionPoints`，模擬「回合已經輪回這位玩家，且已站在有操作效果的房間裡」，不必真的跑完整輪的兩位玩家回合交換。修正後測試通過，繼續完成 Task 5 剩餘實作與全套回歸測試。
