# 山中小屋（Betrayal at House on the Hill）網頁多人版 — 設計文件

日期：2026-07-31
狀態：已與開發者確認，待寫入實作計畫

## 1. 專案目標

將實體桌遊「山中小屋」移植為可供多人連線遊玩的網頁遊戲。定位為**技術學習專案**，同時**實際供開發者朋友圈連線遊玩**。長期目標是保留「擴充自創劇本」的彈性，讓開發者之後能以原版機制為基礎，創作原創劇本（不同故事包裝、不抄襲版權內容）。

## 2. 使用情境與限制

- 對象：開發者本人（新手，主要由 Claude Code 協作開發）＋固定朋友圈，非公開產品，不需帳號系統。
- 連線：需同時支援「同一 WiFi/區網」與「各自透過外網連線」，兩者使用同一份程式碼，差別只在部署方式（本機執行 vs 部署到雲端主機）。
- 視覺風格：簡極文字/圖形介面，不做仿實體卡牌美術，優先確保機制與同步邏輯正確。
- 內容來源：開發者提供的規則書/陣營手冊 PDF，由 Claude Code 協助整理抽取為結構化資料，**僅供私人非商業用途**，不對外公開發布。若專案未來考慮公開，需另外處理版權問題。

## 3. 整體架構

Node.js 單一伺服器同時作為靜態檔案/API（Express）與即時通訊層（Socket.IO），並持有「權威遊戲狀態」；React（Vite）前端只負責顯示伺服器允許該玩家看到的資料。

```
┌─────────────────────────────────────────┐
│              Node.js 伺服器                │
│  ┌─────────────┐  ┌──────────────────┐   │
│  │  Express     │  │   Socket.IO       │   │
│  └─────────────┘  └──────────────────┘   │
│              ↓                            │
│      ┌───────────────────┐                │
│      │   遊戲引擎（權威狀態）│                │
│      └───────────────────┘                │
└─────────────────────────────────────────┘
              ↑↓ WebSocket
┌─────────────────────────────────────────┐
│   React 前端（每個玩家瀏覽器一份）           │
└─────────────────────────────────────────┘
```

**核心原則**：伺服器是唯一真相來源（single source of truth）。所有操作先經伺服器驗證再生效並廣播；前端不做任何規則判斷，避免隱藏資訊（如叛徒身份）透過前端程式碼外洩。

**Phase 2 預留**：遊戲引擎只對外暴露一組「玩家操作函式」（`submitMove()`、`drawCard()`、`endTurn()` 等）。Socket 事件處理器呼叫這組函式；未來的 AI 玩家模組（呼叫 Claude API 決策）也呼叫同一組函式。引擎不需要知道操作來源是人類還是 AI。此階段**只建立這層抽象，不實作 AI 決策邏輯本身**。

## 4. 擴充性設計：劇本與角色外掛系統

原版 50 個鬼屋劇本與開發者未來的原創劇本，在架構上一視同仁，皆透過同一套外掛介面接入，核心引擎不因特定劇本而修改。

**共用效果語言**（宣告式、資料驅動）：房間效果、道具/事件/預兆卡效果以結構化資料描述，涵蓋屬性增減、移動、抽卡、擲骰檢定、條件分支、取得/失去道具等常見類型。新增卡牌內容只需寫資料，不動引擎程式碼。

**劇本模組（Scenario Module）**：每個劇本是獨立資料夾：
- `manifest.json`：劇本標題、叛徒/生還者分配規則、各陣營勝利條件文字、新增房間/道具/NPC 資料
- `logic.js`：劇本專屬掛勾邏輯（如 `checkVictory(state)`、`onTurnStart(state, player)`），供效果語言無法涵蓋的自訂規則使用

**角色模組（Character Module）**：套用同樣的「資料 + 掛勾邏輯」模式，用於角色專屬特殊能力/技能（開發者原創劇本中「多人合作角色」需求）。

**NPC/敵對實體**：核心引擎提供通用「場上實體」抽象（位置＋屬性＋簡單行為掛勾），劇本模組可生成並操控此類實體，供敵對 NPC 使用。

範圍確認：開發者原創劇本沿用既有機制類別（翻房間、房間效果、屬性調整、道具卡、NPC、合作陣營），**不規劃**全新資源系統或與原版完全不同的核心玩法；主題創新以「靈異 → 兇案解謎/密室逃脫」的包裝轉換為主。此範圍下，上述外掛彈性已足夠，不需為假設性更大彈性而過度設計。

## 5. 伺服器端元件

- **大廳管理 (Lobby Manager)**：建立/加入房間、房號、連線追蹤、玩家順位指定
- **內容載入器 (Content Loader)**：啟動時讀取共用卡牌/房間資料，以及選定的劇本模組、角色模組
- **遊戲核心 (Game Engine Core)**：持有所有場上實體、房間拼圖狀態、牌庫狀態、回合順序、預兆計數；對外暴露操作函式（供 Socket 層與未來 AI 層共用）
- **效果解析器 (Effect Resolver)**：執行宣告式效果，是卡牌/房間效果的共用執行引擎
- **劇本/角色掛勾執行器 (Hook Runtime)**：在特定時機呼叫目前啟用的劇本/角色模組自訂邏輯
- **狀態視角過濾器 (State View Filter)**：依「這個玩家該看到什麼」過濾完整狀態後才送出，是隱藏資訊不外洩的關鍵把關點
- **Socket 事件層**：薄層，只負責轉呼叫遊戲核心操作函式，不含規則判斷

## 6. 客戶端元件（React）

大廳畫面、樓層房間拼圖顯示（地上/樓上/地下室分頁）、玩家屬性/道具/技能面板、當下合法操作按鈕（由伺服器動態告知）、卡牌/事件彈窗、鬼屋降臨揭曉畫面（依角色顯示不同內容）。

## 7. 資料流程

**一般回合**：伺服器廣播目前輪次 → 玩家移動（未探索房間則抽房間磚）→ 房間效果解析（可能觸發抽事件/道具/預兆卡）→ 若抽到預兆卡則計數 +1 並擲骰比對是否觸發鬼屋降臨 → 玩家可用道具/技能 → 結束回合。

**鬼屋降臨（隱藏資訊揭露）**：依「最後預兆卡＋觸發房間」查表選定劇本模組 → 依模組規則分配叛徒/生還者陣營 → **各玩家 socket 分別收到只屬於自己的陣營資訊**（叛徒收到專屬秘密勝利條件，生還者收到公開任務目標，彼此看不到對方私密內容）→ 之後每個行動後呼叫劇本 `checkVictory()`，達成條件即結束遊戲並公開結果。

## 8. 內容資料格式（範例）

```json
// 房間磚
{ "id": "room_conservatory", "floor": "ground", "name": "音樂室",
  "text": "...", "drawType": "item", "effects": [...] }

// 道具/事件/預兆卡
{ "id": "item_dagger", "type": "item", "name": "...",
  "text": "...", "effects": [{ "type": "stat_change", "stat": "might", "delta": 1 }] }
```

效果詞彙涵蓋：`stat_change`、`move`、`draw_card`、`dice_check`、`conditional`、`add_item`、`remove_item`；超出詞彙的特殊邏輯用 `custom_hook` 指向劇本/角色模組的自訂函式。

## 9. 開發者劇本輸入介面（後期階段）

不建置圖形化編輯器。採用「樣板資料夾 + 結構驗證工具」：

```
data/scenarios/<scenario-id>/
  manifest.json   # 劇本中繼資料、勝利條件文字、新增房間/道具卡/NPC
  logic.js        # 掛勾函式實作，依文件化介面（JSDoc 註解）撰寫
  README.md       # 開發者自用設計筆記，非遊戲內容
```

搭配兩個指令：
- `npm run new-scenario <id>`：產生上述樣板資料夾，欄位附註解範例
- `npm run validate-scenario <id>`：載入前檢查 manifest 格式（缺欄位、型別錯誤、引用的房間/道具 ID 是否存在），錯誤訊息需明確指出「哪個檔案、哪個欄位」

此設計對應開發者「本人 + Claude Code 協作」的工作模式：以文字描述劇本內容，由 Claude Code 依固定 schema 產生/填寫檔案。不考慮非技術背景協作者，故不建置網頁表單或視覺化編輯器。

## 10. 錯誤處理與重新連線

- 每個操作先經伺服器驗證合法性，不合法只回傳錯誤給發送者，不影響遊戲狀態
- 玩家斷線重連：瀏覽器保留房號＋個人識別 token，重連時伺服器比對 token 找回原本狀態，重送該玩家專屬過濾後畫面
- MVP 階段不處理伺服器程序本身當機的狀態保存（純記憶體儲存），為刻意的範圍限縮

## 11. 測試策略

- 單元測試（Jest）：效果解析器各類效果、牌庫洗牌/抽牌（固定亂數種子）、預兆/鬼屋觸發比對表
- 重點測試：狀態視角過濾器，確保任何情況下玩家 A 拿不到玩家 B 的秘密資料
- 整合測試：多個 Socket.IO 測試客戶端模擬完整一輪流程，含劇本 `checkVictory()` 觸發遊戲結束
- 前端以手動找朋友實測為主，不特別做自動化 UI 測試

## 12. MVP 範圍

**包含**：
- 房間拼圖（地上/樓上/地下室三層牌庫）
- 角色屬性（力量/速度/知識/理智）與部分標記前進/後退
- 事件卡/道具卡/預兆卡抽取與效果
- 部分逐字描述的閃遷邏輯
- 預兆計數 + 鬼屋降臨比對
- 1-2 個完整原版劇本（含叛徒/生還者分陣營、單獨勝利條件）
- 劇本/角色外掛介面（供上述劇本驗證，也為未來擴充打底）
- 樣板資料夾 + 驗證工具（供後續新增劇本使用）

**不包含**：
- 其餘 48+ 原版劇本內容
- AI 玩家（Phase 2）
- 伺服器狀態持久化/斷線後完整存檔
- 帳號系統、公開部署所需的安全強化

## 13. 未來階段

- **Phase 2：AI 玩家**（呼叫 Claude API 做決策，2 真人 + 2 AI 可運作）。依賴 MVP 已建立的「玩家操作函式」抽象，僅需新增 AI 決策模組呼叫同一組函式。
- **Phase 3+：原創劇本擴充**，主題朝兇案解謎/密室逃脫方向創作，沿用第 4 節的劇本/角色外掛系統與第 9 節的樣板+驗證工具。
