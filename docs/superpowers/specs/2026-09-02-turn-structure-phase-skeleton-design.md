# 回合制改為「各自回合同時行動」— 核心骨架設計文件（M2E 第一子專案）

## 目標

取代現有的嚴格輪流制（一位玩家行動完才輪到下一位），改成「全局角色（真人玩家＋NPC）在同一輪內依固定階段順序、各自同時行動」的回合制骨架。這是 Handover 項目14的第一個子專案——範圍刻意限定在「階段骨架本身」（階段列表、行動力怎麼跨階段分配、階段怎麼推進、結算階段的角色），不含「互動階段實際怎麼結算」「既有機制逐一歸類到哪個階段」「倒數計時的實際 UI／伺服器基礎建設」「NPC操控機制的實作」——這些都是骨架定案後各自獨立的後續子專案。

## 動機

現行輪流制加上未來 NPC（犬靈、邪祟後怪物）的行動順序，會讓玩家等待時間拉得很長，原本規劃用倒數計時控制單一玩家的行動時間，但 NPC 加入後回合數變多，等待問題依然存在。改成回合制讓所有真人玩家跟 NPC 在同一輪內同時行動，可以有效縮短等待時間。

## 現況（輪流制）

目前 `gameState.turnOrder`（玩家 id 陣列）＋`gameState.currentPlayerIndex` 決定「誰的回合」，`getCurrentTurnPlayerId()` 是唯一的回合擁有權判斷依據，`server/src/socketHandlers.js` 裡幾十個 handler 各自用 `getCurrentTurnPlayerId(gameState) !== playerId` 擋下非當前玩家的操作。同一時間**只有一位玩家能行動**，所以完全不需要處理「兩人同時修改同一份資料」的並發情境。`advanceTurn`（`turnFlow.js`）處理換人＋行動力重置（依速度屬性算出 4-8 點不等）。

## 新架構：五階段回合制

每一輪固定依序走五個階段，不可跳過或改變順序：

**玩家移動階段 → NPC移動階段 → 玩家互動階段 → NPC互動階段 → 結算階段**

**分類原則**：一個行動/效果會不會影響「自己以外的角色」，決定它屬於移動階段還是互動階段——
- **不影響其他角色**（移動、搜索、房間效果、預兆、考驗等，涵蓋目前 M2 已完成的幾乎所有機制）：留在對應的移動階段，**在該階段當下立即生效**，不延後
- **會影響其他角色**（M3 攻擊/傷害為主，也包含現有「給予道具」「對他人使用道具」這類 `canTargetOthers` 機制）：進對應的互動階段，效果**延後到結算階段才生效**

玩家跟 NPC 的移動/互動各自獨立成一個階段（不合併），因為玩家可能同時操控自己的角色跟一個 NPC（例如犬靈），分開階段可以避免同一個人在同一個時間點要操作兩個不同實體造成混亂。

## 行動力分配

沿用現有單一共用行動力池（依速度屬性 4-8 點不等，這個不對稱性是刻意設計，不是要修正的問題）：
- 玩家移動階段沒花完的行動力，可以帶進玩家互動階段繼續用
- 玩家互動階段沒花完的行動力，**歸零**，不會留到下一輪
- 互動階段**鎖定不能移動**（避免襲擊目標在互動階段當中移動消失，造成結算時目標不存在的錯誤）
- NPC 的行動力池規則跟玩家完全一致（NPC移動→NPC互動同一套carry-over/歸零規則）

依開發者明確要求：這個設計是刻意讓玩家必須謹慎規劃行動力分配（先移動到對的位置、再決定要不要行動），是遊戲重要的策略成分，不是要簡化掉的複雜度。

## 換階段機制

**時間到，或該階段所有玩家/NPC都按下「結束」鎖定，兩者任一發生就進下一階段**（不是純粹倒數，也不是純粹等全體確認，是兩者取先發生的）。沿用現有「結束回合」按鈕的概念，改成每個階段各自有自己的「結束本階段」按鈕，按下後鎖定該玩家/NPC在本階段的行動。倒數秒數之後另外定義（不在這份骨架文件的範圍內）。

## 結算階段

結算階段沒有任何玩家操作——伺服器自動運算所有互動階段累積下來的效果（實際運算規則，例如傷害/治療怎麼加總抵消，留給後續子專案定案），運算完成後用結果彈窗顯示給每位玩家，玩家各自按確認。全體確認後，開始新的一輪（重新從玩家移動階段開始，行動力重置）。

## 跟 NPC 操控機制（Handover 項目8）的整合

2026-09-01 的 NPC 操控機制設計文件（[2026-09-01-npc-control-mechanism-design.md](2026-09-01-npc-control-mechanism-design.md)）保留了兩塊待定：NPC 回合怎麼插入、NPC 回合的操控權授權。這份骨架文件解決了第一塊——**NPC 不是插在操控者本人回合後面，而是有自己獨立的全局階段（NPC移動階段／NPC互動階段）**，操控者在對應階段透過自己的連線送出 NPC 的動作。操控權授權（`getCurrentTurnPlayerId() !== playerId` 對 NPC 會誤判的既有問題）在這個新模型下需要重新設計——現在不是「誰的回合」而是「現在是哪個階段、這個玩家/NPC在這個階段有沒有被鎖定」，實際判斷邏輯留給後續子專案（NPC整合實作）處理。

## 已知技術風險：並發存取

現有架構同一時間只有一位玩家能行動，完全不用處理並發修改同一份資料的情況。改成同一階段內所有玩家可以同時送出動作後，會出現真正的並發情境——例如兩位玩家同時搜索同一間房、同時想撿同一件房間掉落物。**開發者已確認處理原則：先到先得（先送達伺服器的請求先處理，後到的請求視當下狀態可能失敗或得到不同結果）**。實際的並發安全機制（例如伺服器內部怎麼序列化處理同時湧入的請求、失敗時要回傳什麼錯誤給後到的玩家）留給後續子專案（既有機制逐一歸類/實作階段）設計。

## 範圍排除（留給後續各自的子專案）

- **互動階段結算的實際運算規則**：傷害/治療怎麼加總抵消、非數值互動（偷道具/給予道具）在同一階段內怎麼處理衝突——這是下一個要討論的子專案
- **既有機制逐一歸類到移動階段或互動階段**：現有 50+ 個效果類型、所有卡片/房間資料，要一個個確認屬於哪個階段，這是資料量很大的獨立工作
- **倒數計時的實際 UI 與伺服器基礎建設**：每階段的秒數、伺服器怎麼廣播倒數、client 怎麼顯示
- **NPC 操控機制的實際實作**：資料模型／行動範圍等已在 2026-09-01 的設計文件確認，回合插入問題這份文件解決了，但操控權授權的實際程式碼、跟這份骨架的串接，都還沒寫
- **並發安全機制的實際實作**：見上方「已知技術風險」，原則已定但程式碼設計留待後續
- **現有 701 個測試的遷移**：這些測試大多假設嚴格輪流制，新模型上線後需要大幅改寫，不在這份骨架文件範圍內
