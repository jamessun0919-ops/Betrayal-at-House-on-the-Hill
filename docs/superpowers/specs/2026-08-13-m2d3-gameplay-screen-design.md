# M2D3：遊戲進行畫面（地圖＋人物面板骨架）設計文件

## 背景與目標

M2D1（大廳流程）、M2D2（角色選擇正式畫面）皆已完成並合併進 `main`。全員選完角色後，目前轉場目標是除錯頁面 `DebugGameScreen.jsx`（純文字/JSON 呈現，東西南北四個固定按鈕、道具/操作/攻擊/結束回合/樓梯按鈕，沒有地圖視覺化）。本文件設計正式的遊戲進行畫面，取代除錯頁面。

**本次設計範圍**：畫面整體版面骨架＋地圖顯示機制＋房間美術圖產生規則。行動選單細節、擲骰道具介入 UI、操控實體切換 UI、道具互動細節等留到後續分項討論（見「範圍外事項」）。

## 整體版面

畫面分左右兩區：左 2/3＝地圖區，右 1/3＝人物面板（屬性／物品／訊息）。

## 地圖區：聚焦模式（預設、唯一常駐畫面）

- 主視覺＝玩家目前所在房間的完整美術圖（見下方「房間美術圖產生規則」）
- 房間四個邊：有門的邊顯示對應方向的移動按鈕，取代除錯頁面現有的固定東西南北按鈕；無門的邊不顯示按鈕
- 門按鈕依「移動到已探索房間」（`kind:'move'`）／「開新門抽新房間卡」（`kind:'open_door'`）用不同樣式／圖示區分（例如：開著的門框 vs 關閉的門／問號圖示），對應伺服器 `turnFlow.js` 的 `getAvailableDirections` 已經算好的兩種 kind
- 已探索的鄰居房間：在對應邊緣顯示裁切／淡化的局部畫面（讓玩家知道那裡有房間，不需要完整呈現鄰居房間全貌）；開新門方向不顯示鄰居預覽（房間內容還沒抽出來，不存在）
- **沒有常駐的整體地圖**——畫面預設永遠只聚焦目前房間＋鄰居一角，不會因為地圖範圍變大就自動縮放或平移整層樓

## 地圖區：總覽模式（按鈕切換）

- 額外提供一個按鈕切換到簡化格狀地圖：依真實 `x,y` 座標排列，色塊＋房間名稱文字即可，不需要精緻美術
- **總覽地圖是「玩家個人」的探索紀錄，不是全體玩家共用的**：只顯示操作者自己走過的房間，不是遊戲裡任何玩家探索過的房間聯集
- 樓層切換（地面層／樓上——目前資料結構只有這兩層，沒有地下室，`board.ground`/`board.upper`）

## 人物徽章

- 玩家在地圖上（聚焦模式或總覽模式皆同）以圓形徽章標示，圖檔由開發者提供、暫時佔位
- 多名玩家同處一室：這次骨架先簡單並排顯示，不做精緻碰撞排版

## 右側面板骨架（只定版位，互動細節留後續分項討論）

- 上：自己的 4 項屬性（沿用 Handover 已定案的長條圖＋刻度呈現，不只顯示原始數字）
- 中：道具清單（**現在也包含預兆牌**，見 Handover 除錯注意事項）
- 下：訊息／事件記錄區——前端自行維護的捲動清單（伺服器目前沒有事件歷史記錄機制，這是純前端責任）
- 行動按鈕（道具／操作／攻擊／結束回合／樓梯）先沿用除錯頁面既有事件呼叫邏輯搬過來排版，互動細節留後續

## 房間美術圖產生規則

### 風格選定過程

依序測試三種等角／俯視風格（實際生圖比較見對話紀錄，本文件只記錄結論）：
1. 等角透視娃娃屋（只畫遠側兩面牆，走入視角）——氛圍最好，但近側兩面牆完全沒畫出來，無法支援四面牆都放門框
2. 等角透視地牢圖磚（四面牆等高可見，但仍有景深傾斜）——單張圖無法用簡單旋轉對應不同門位置組合（旋轉會破壞透視/光影邏輯）
3. **完全平面俯視圖（無透視傾斜、無立體景深、光線無方向性）—— 確定採用**：解決了「單張圖可以旋轉對應任意門位置」的需求，且開發者測試禮拜堂範例後確認視覺效果可接受

### 固定風格區塊（每張房間圖逐字複用）

```
1920年代鬼屋題材房間圖磚，完全正上方俯視角度（無透視傾斜、無立體景深，牆面畫成建築平面圖式的純平面線條），俯視遊戲地圖圖磚風格，手繪遊戲美術質感。四面牆body統一畫成較薄的規格（比獨立房間視覺合理厚度再薄一半，兩間房並列時兩片薄牆會加成正常厚度）。門框開口與大型家具的牆面配置，依下方【本房間配置】指示，未指定為門框的牆面一律畫成完整實牆。色調沉悶不飽和——暖棕色、褪色米色、灰塵灰、深色陰影。光線要平均、不要有明顯方向性。正方形 1:1 構圖，房間牆面直接頂到畫面四個邊緣，不留任何背景留白，只畫這一間房間，不要出現人物或怪物。這是一整套房間圖磚其中一張，鏡頭角度、牆面高度／厚度、門框位置與大小要維持固定，供整套房間套用同樣規格。
```

### 變動變數區塊（每間房間依 `rooms.json` 的 `doors` 欄位填寫）

每間房間的變動內容包含：
- **本房間配置**：哪幾面牆留門框開口、哪幾面牆是實牆、哪幾面牆放大型家具（增加畫面生動感）
- **房間內裝潢**：依房間類型與 1920 年代背景描述的家具/物件，維持原本 prompt 已經在用的具體歷史風格細節（開發者確認要保留這部分內容品質）

### 門型變體策略（依 `doors` 數量決定要不要多出變體圖）

`rooms.json` 的 `doors` 欄位只記錄「門的數量」，實際門開在哪幾側是每局遊戲執行期間才隨機決定（`server/src/game/doorLayout.js` 的 `computeDoorLayout`）。單張圖要能對應「任意方向」，靠的是**渲染時依照這局真實的門資料，旋轉圖片對齊**，不是圖片本身畫死方向。

- **`doors:1`（3 間房）**：只有一種相對形狀（1 門＋3 牆），出 1 張圖，遊戲中依實際方向旋轉套用
- **`doors:2`（17 間房）**：2 門的相對位置有「相鄰」「相對」兩種形狀，兩者無法互相旋轉得到，**出 2 張變體圖**（相鄰版、相對版），遊戲中依實際是哪一種形狀挑對應變體，再旋轉對齊精確方向
- **`doors:3`（5 間房）**：只有一種相對形狀（3 門＋1 牆，哪一側是牆不影響形狀），出 1 張圖，旋轉套用
- **`doors:4`（6 間房）**：四面都是門，沒有形狀變化，出 1 張圖，不需要旋轉邏輯（也不能有排除牆，見下）

總計約 3×1 + 17×2 + 5×1 + 6×1 = **48 張圖**（不是 31 張），開發者需要分批生圖，跨批次要盡量維持風格一致（靠固定風格區塊逐字複用達成）。

### 房間專屬「排除牆」（例如禮拜堂祭壇牆永遠不放門）

部分房間有明確的主題方向性（例如禮拜堂的祭壇＋彩繪玻璃窗那面牆，現實邏輯上不該是出入口），可以在該房間的**每一個變體圖**裡都把該面牆固定畫成實牆，不留門框。

**技術結論（已推導確認，不需要新增任何後端程式碼／資料欄位）**：只要排除牆在原圖裡本來就是「牆」的身分（不是門），不管這局遊戲隨機出來的真實門位置組合是什麼，渲染時永遠可以選到一個旋轉角度，讓圖片的門框們對齊真實門的位置，這時排除牆會自動落在真實資料剩下的「牆位置」上——因為旋轉是整張圖一起轉、圖片內部「門／牆」的相對關係不會被打散，而真實遊戲資料裡任何一面牆都是等價的（沒有哪一面牆比較適合放祭壇的限制）。

**唯一限制**：只有 `doors ≤ 3` 的房間可以設定排除牆（`doors:4` 的房間四面都是真實的門，邏輯上沒有牆可以放）。

**範例（禮拜堂，`doors:2`，兩個變體）**：

變體 A（相對）：
```
本房間配置：四面牆中，上方牆面（祭壇牆）為實牆，左、右兩面牆中央各留一個門框開口，下方牆面為實牆。下方牆面放置一組大型家具（長椅排）。
房間內裝潢：木製長椅面向小祭壇，祭壇後方一扇彩繪玻璃窗，積灰的燭台，一個倒地的十字架。
```

變體 B（相鄰）：
```
本房間配置：四面牆中，上方牆面（祭壇牆）為實牆，右、下兩面牆中央各留一個門框開口，左面牆為實牆。左面牆放置一組大型家具（長椅排）。
房間內裝潢：木製長椅面向小祭壇，祭壇後方一扇彩繪玻璃窗，積灰的燭台，一個倒地的十字架。
```

排除牆不是每間房都需要，預設所有房間四面都可以放門框，只有明顯有主題方向性的房間才特別標註排除牆。

## 需要新增的後端資料串接（架構缺口，非本次討論範圍，但實作計畫要納入）

盤點現有程式碼發現兩個目前完全沒做的缺口：

1. **前端目前完全拿不到房間靜態內容（名稱等），只有 `roomId` 字串**：`gameState.js` 的 `serializeGameState` 只送 `{roomId, x, y, doorSides, droppedItems}`，房間名稱／文字等內容從未傳給前端。需要比照角色選擇畫面已經在用的模式（伺服器把完整內容陣列送給前端），新增一個管道讓前端能把 `roomId` 換成房間名稱／對應美術圖檔名。
2. **`getAvailableDirections`（`kind:'move'`/`kind:'open_door'`）已經在伺服器端寫好，但完全沒有透過 socket 傳給前端**：`turnFlow.js` 已 export 這個函式，只是 `socketHandlers.js` 完全沒有用到它回傳前端。需要新增一個管道讓前端知道目前房間四個方向各自的門狀態，用來畫對應樣式的門按鈕。
