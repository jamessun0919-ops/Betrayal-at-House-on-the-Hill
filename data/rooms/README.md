# 房間資料填寫說明

`rooms.json` 放 MVP 測試版會用到的房間磚資料，目前共 23 筆。

## 欄位格式

```json
{
  "id": "room_chapel",
  "name": "禮拜堂",
  "description": "",
  "floor": "ground",
  "drawType": "omen",
  "text": "若在此房結束回合，可獲得1級意志。每位探險者在遊戲中只能受益於此房一次。",
  "effects": [
    { "type": "stat_change", "stat": "sanity", "delta": 1, "onceOnlyPerPlayer": true }
  ],
  "needsCustomLogic": false
}
```

- `description`：**新增欄位，目前全部空白，等開發者填寫**。這是角色第一次走進這間房間時顯示的敘述性文字（營造氣氛用，跟 `text` 的機制規則文字是分開的兩件事），例如「陰暗潮濕的石室，牆上爬滿了不知名的黴斑…」這種場景描述。同一間房只在該玩家第一次進入時顯示一次。
- `floor`：`"ground"`（一樓）/ `"upper"`（二樓）/ `"any"`（一二樓皆可，依開發者確認的通用房間規則）
- `drawType`：每張房間磚背面標示走進這間房要抽哪一種牌（`"event"`/`"item"`/`"omen"`），已由開發者對照實體元件填完；如果之後新增房間沒有標示要抽牌，就填 `"none"`
- `text` / `effects`：跟 `data/cards/README.md` 的格式一樣，機制規則文字＋效果詞彙。已知效果的房間（禮拜堂/圖書室/食品儲藏室）已填好；純粹普通房間 `effects` 留空即可
- `needsCustomLogic`：塔橋（雙側阻擋，需力量考驗才能通過另一側）、保險庫（知識考驗6+開啟、抽2張道具卡、放空蕩標記）這種不是單純「屬性增減」的多步驟機制，標記為 `true`，`effects` 留空，之後跟開發者一起討論怎麼實作

## 樓層分配說明（附加背景，非資料本身需要的欄位）

這 23 個房間裡，6 個是劇本1/10 直接需要的，其餘是額外增加隨機性用的。樓層判斷大多是低信心猜測（因為規則書沒有完整的樓層對照表），其中多個房間（廚房/廢棄的房間/食品儲藏室/臥房/傭人房/焦黑的房間/染血的房間/健身房/武器室/標本室/舞廳）依開發者確認，遊戲機制上是「一二樓皆可」的通用房間磚。若之後發現有房間的樓層猜錯，直接改 `floor` 欄位即可。

刻意排除的地下室相關房間（因為 MVP 測試版不含地下室）：地下湖、地底深淵、地下墓穴、來自地下室的樓梯、酒窖。
